## Remaining limits and risks

- A protected Preview and actual browser acceptance are still required: real HTTPS SIWE cookies, wallet extension/mobile behavior, CSP hydration, Vercel header trust, PostgREST access, database persistence and denied direct browser database access. Initial Preview scope uses installed browser wallets; WalletConnect and contract-wallet transaction acceptance remain separate checks.
- CSP retains `style-src 'unsafe-inline'` for existing React style attributes and optional wallet UI. Production **scripts** have no unsafe-inline/eval. WalletConnect's finite optional list still needs real-device acceptance; do not broaden it speculatively.
- The service key bypasses RLS. The server remains responsible for wallet/collection authorization; audit/revision rows are not tamper-proof against a compromised service credential. Restrict credential and operator access and define retention/backup/alerting before public release.
- Distributed quotas bound expensive operations; in-process concurrency does not create a global concurrency lock across serverless instances. Protected Vercel access is required. These controls do not promise resistance to a distributed flood or make Origin checking bot authentication. Public release needs measured traffic/load limits and operational monitoring.
- GitHub private-repository rulesets are plan-restricted (read returned HTTP 403). No purchase or public visibility change was made. Use explicit successful-CI commit pinning and disabled automatic deployments for the protected preview; revisit enforceable release controls before public access.
- Public minting/mainnet blockers remain: granular network/action/collection/value/expiry release policy, atomic publication reservation, receipt finality/reorg/replacement handling, payment-token semantics and limits, independent transaction review, and controlled acceptance on every network. They are outside this protected-preview remediation stage, and the hard write locks keep them unreachable here.
